## The machine, in one picture

```
                    ┌──────────────── score.py: run() ──────────────────┐
  {data, user_type} │                                                   │
        └──────────►│  ner_helper.run_ner()                             │
                    │    ①  MATERIAL_ID regex        :779  ──┐          │
                    │    ②  data_preprocessing()     :823    │ any hit  │
                    │    ③  FEATURE (pfas-free)      :893    │    =     │
                    │    ④  GRADE fast path          :938    ├─► RETURN │
                    │    ⑤  COMPETITOR_GRADE         :1089   │  no LLM  │
                    │    ⑥  AUTO_CERT                :1140  ─┘          │
                    │                  ↓ nothing matched                │
                    │    ⑦  get_entities()  →  Azure OpenAI      :1263  │
                    │    ⑧  validate_result_dict()               :1293  │
                    │    ⑨  ~600 lines of correction rules  :1295-1885  │
                    │    ⑩  identify_out_of_scope_items()        :1886  │
                    │    ⑪  de-duplicate every list              :1901  │
                    └───────────────────────────────────────────────────┘
```

**Steps ①–⑥ are whole-query short-circuits.** If one fires, everything after it is skipped —
including, for three of them, the out-of-scope check.

# GROUP A — resolved without the LLM

## 1. `21234567` — the only entity with no reference data

**Route: FAST-PATH MATERIAL_ID** ✅ RUN

| Step | Line | What happens |
|---|---|---|
| strip | `:778` | `"21234567"` |
| digits only? | `:779` | `isdigit()` → True |
| drop padding | `:781` | `str(int(...))` → `"21234567"` |
| 8 chars, starts 2/5? | `:783` | True → **return** |

**Dependency data used: none.** Not one file is consulted.

```jsonc
"entities": { "MATERIAL_ID": ["21234567"], /* all 16 others empty */ },
"outOfScope": { "active": false }          // hardcoded at :807 — never computed
```

**Lesson.** The only purely structural entity. It also **skips the out-of-scope check entirely** —
`active:false` is written literally, not derived. Three of the six fast paths do this (`:807`,
`:924`, `:1182`); only GRADE and COMPETITOR_GRADE actually call the scope filter.

## 2. `000000000021234567` — why `int()` is in there

**Route: FAST-PATH MATERIAL_ID** ✅ RUN — normalises to `21234567`

SAP exports pad material numbers to 18 characters. `str(int(...))` at `:781` drops the zeros
before the length test. Without it, `len(...) == 8` would fail and the query would go to the LLM,
which has never been trained to emit `MATERIAL_ID`.

**Lesson.** One function call absorbs an entire class of copy-paste input.

## 3. `pfas-free` — the fast path that compares the *raw* query

**Route: FAST-PATH FEATURE** ✅ RUN (was un-runnable before the 11-Aug commit — see below)

```python
# ner_helper.py:893-898
for f in NORMALIZED_UNIQUE_VALUES['FEATURE']:
    if search_query == f[0] or search_query in f[1]:
        if f[0] == 'pfas-free':
            pfas_flag, feature = True, 'pfas-free'
```

Two things worth noticing:

**It compares `search_query`, not `search_query_cleaned`.** This check sits at line 893, *before*
`data_preprocessing()` output is used anywhere. And that is deliberate — cleaning would break it:

```
raw:      'pfas-free'
cleaned:  'pfas - free'      ✅ RUN — add_spaces() splits the hyphen
```

`'pfas - free'` would not equal `'pfas-free'`, so comparing the cleaned form would fail.

**Only `pfas-free` returns.** The loop matches *any* feature and stores it in `feature`, but only
the PFAS branch sets `pfas_flag`, and only `pfas_flag` triggers the return at `:900`. Every other
single-feature query falls through to the LLM. Despite appearances this is a **pfas-free fast
path**, not a feature fast path.

> ✅ **Fixed on 11-Aug.** `NORMALIZED_UNIQUE_VALUES['FEATURE']` used to be absent from the data
> file, so this line raised `KeyError` on every query. The key now exists with 41 entries shaped
> `[canonical, [synonyms]]`, and the route verifies:
>
> ```
> pfas-free   ->   FAST-PATH FEATURE      (previously fell through to the LLM)
> ```
>
> See [`16-…`](16-entity-by-entity-resolution.md) §28 for the full story, including the two
> file corruptions that had to be repaired before it parsed.

## 4. `celanex 2002-2` — the plain exact match

**Route: FAST-PATH GRADE via `:953`** ✅ RUN

| Step | Line | Value |
|---|---|---|
| clean | `:823` | `'celanex 2002-2'` |
| normalise (offsets + punctuation) | `pre_processing.py:208` | `'celanex20022'` |
| guards | `:941-945` | all pass |
| strip punctuation from cleaned | `:949` | `'celanex20022'` |
| **exact in `NUV['GRADE']`** | `:953` | **hit** → `no_offsets = True` |
| rebuild name | `:1015` | `'celanex 2002-2'` |
| scope check | `:1049` | in scope → kept ✅ RUN |

**Data used:** `normalized_unique_values_for_grade_mapping.json` → `GRADE` ·
`outOfScopeData.json` → `gradesInScope` · `oos_color_code_pattern.txt` (not reached — the grade
was found in-scope at step 1).

**Lesson.** `no_offsets=True` at `:955` tells the reconstruction step to use the whole cleaned
query rather than dropping words from it. The `" - "→"-"` restore at `:1025` is what keeps
`2002-2` from coming back as `2002 - 2`.

## 5. `looking for alternative to celanex 2002-2` — same answer, different door

**Route: FAST-PATH GRADE via `:956`** ✅ RUN

```
cleaned:     'looking for alternative to celanex 2002-2'
normalised:  'celanex20022'        ← looking / for / alternative / to all removed
```

`normalize_query()` (`pre_processing.py:208-225`) drops all 34 **`GRADE_OFFSET_TERMS`**
(`pre_processing.py:6`) *before* stripping punctuation. That is the whole reason a sentence-shaped
query can still hit an exact-match fast path.

Note it matched at `:956`, not `:953` — because `search_query_normalized` (line 949) keeps the
offset words, so `'lookingforalternativetocelanex20022'` is not in the list. The offset-stripped
form is.

The grade name is then rebuilt at `:1017-1019` by removing the same offset terms from the cleaned
text.

**Lesson.** *"alternative to X"*, *"tds for X"*, *"replacement for X"* all collapse to `X`. This
one list is why the fast paths fire on real user language at all.

## 7. `ms50017cpn5448` — a spec number that knows its own carmaker

**Route: FAST-PATH AUTO_CERT via `:1151`** ✅ RUN → **`oem = stellantis-chrysler`**

|---|---|---|

## 8. `pa66gf30` — a guard earning its keep

**Route: LLM — fast paths blocked by `non_grade_patterns`** ✅ RUN

The string is a **polymer + filler load**, not a grade name. Pattern 4 of the twelve at `:873-888`
matches:

```
^(pps|…|pa66|…)((\d+)(cf|gf|…)?|(cf|gf|…)(\d*))$
   └─ pa66 ─┘   └────────── gf30 ──────────┘
```

Without this guard, `pa66gf30` would substring-match some real grade at `:958` and short-circuit
to a **wrong single GRADE**, with every other entity empty. The comment at `:874` records the
lesson in the source: *"order matters… `v1810` will get formatted to `v1, 810` which is wrong as
it is partial string of `kynar hsv1810`"*.

**Lesson.** The guards are not defensive padding — they encode naming collisions discovered in
production.

## 9. `gf30` — blocked twice over

**Route: LLM — two guards fail** ✅ RUN

| Guard | Line | Why it fails |
|---|---|---|
| `columnstoIgnore` / `columnsforSubstringCheck` | `:941` | `gf30` is a substring of entries in the 1,022-item ignore list |
| filler-code regex | `:942` | `re.fullmatch(r'(\d+(?:gf\|mf\|gb\|af)\|(?:gf\|mf\|gb\|af)\d+\|…)')` matches |

**Lesson.** Two independent mechanisms catch the same class of input. `columnstoIgnore` is
*data* (regenerable when new collisions appear); the regex is *code*. Belt and braces, because a
false grade match is a silent wrong answer.

## 10. `zytel 101f bk009` — recognised, then refused

**Route: FAST-PATH GRADE via `:953`, then flagged out-of-scope** ✅ RUN (both stages)

This is the most instructive example in the set, because **two opposite things happen**:

```
stage 1  — the grade vocabulary RECOGNISES it
           'zytel101fbk009' IS in NUV['GRADE']   →  fast path fires, GRADE returned

stage 2  — the scope filter REFUSES it            (identify_out_of_scope_items, :1049)
           not in gradesInScope  →  found in grades  →  flagged
```

✅ RUN, both user types:

```
internal   kept={}   active=True   flagged={'GRADE': ['zytel 101f bk009']}
external   kept={}   active=True   flagged={'GRADE': ['zytel 101f bk009']}
```

**Why is a DuPont grade in the Celanese GRADE list at all?** Because **recognition and permission
are deliberately separate stages.** The system wants to understand *"you asked for Zytel 101F"* so
it can respond *"I know what that is, and I can't help with it"* — rather than returning a blank
result. The 21,029-entry grade vocabulary is about comprehension; `outOfScopeData.json` is about
entitlement.

**An ordering trap lives here.** The out-of-scope test at `:596` ends with `continue` (`:599`), so
the colour-code stripper at `:601` — the very thing that would reconcile `BK009` against the
master's `BKB009` — **never runs**. That is bug 217995 in one line. Full walkthrough in
[`17-…`](17-dependencies-files-explained.md) §16.

# GROUP B — resolved by the LLM, then corrected by rules

## 11. `30% glass filled UV resistant nylon 66 with UL94V0` — the canonical query

**Route: LLM** ✅ RUN routing · ⟶ TRACED rules

```
cleaned:  '30% glass filled uv resistant nylon 66 with ul94v0'   ✅ RUN
```

The model returns roughly:

```python
POLYMER:  ["pa66"]                               # canonicalised by the model itself
FILLER:   [{"filler_name": ["glass fiber"]},
           {"total_load": {"value":"30","min":"25","max":"35"}}]
FEATURE:  ["u.v. stabilized or stable to weather"]
PROPERTY: [{"property_name":"flame rating",
            "modifier":{"value":"v-0","min":None,"max":None,"unit":""},
            "property_type":"ul_sub_property"}]
```

Then the rules run:

| Rule | Line | Effect here |
|---|---|---|
| collapse a fake range | `:1295-1303` | `value` kept (30 ≠ min ≠ max) |
| property min/max sanity | `:1325-1333` | no change |
| UL sub-property classification | `:1787-1795` | `flame rating` confirmed `ul_sub_property` |
| unit conversion | `post_processing.py:122` | skipped — unit is `""` |
| de-duplicate | `:1901` | no change |

**The tolerance bands are search tolerances, not specs.** `±5` on a filler load and `±10%` on a
numeric property exist so a 27% glass grade is still found by a *"30% glass"* search.

**Lesson.** On a query like this the rules barely intervene. The heavy rule layer exists for the
*edge* cases, not the happy path.

## 12. `600 V CTI flame retardant PBT` — where UL domain knowledge lives

**Route: LLM** ✅ RUN routing · **PLC conversion** ✅ RUN

The model emits `comparative tracking index (cti)` with `value: 600`, `unit: v`. Then:

| Step | Line | What happens |
|---|---|---|
| unit conversion **skipped** | `post_processing.py:181` | `v` is in the exclusion list `["", "%","v","volt","volts","°c","c","d"]` |
| forced to `ul_property` | `:1797-1802` | `comparative tracking index (cti)` is in `ul_prop_terms` |
| routed by synonym | `:1806, :1813` | `cti_terms` matches |
| **banded** | `cti_value_convertion:359` | `600 → "plc 0"`, min/max set to `None` |

✅ RUN — the real converter:

```
CTI 600 V -> plc 0     CTI 350 V -> plc 2     CTI 120 V -> plc 4
CTI 500 V -> plc 1     CTI 200 V -> plc 3     CTI  50 V -> plc 5
```

**The exclusion list and the converter are two halves of one mechanism.** If volts were converted
to some other unit, the number reaching `cti_value_convertion()` would be wrong. Someone adding
`v` to the conversion table would silently break every CTI search.

**Data used:** `ul_list_name_value.json` (synonyms + legal `plc` values) · both unit-conversion
CSVs (consulted, then skipped).

**Lesson.** UL does not compare raw numbers — it bands them, and **PLC 0 is best**. Note also
`hvtr_value_convertion` runs **inverted** ✅ RUN:

```
HVTR 200 -> plc 4 (worst)      HVTR 20 -> plc 1
HVTR 100 -> plc 3              HVTR  5 -> plc 0 (best)
```

because a *lower* tracking rate is better. Get that backwards and every HVTR search inverts.

## 13. `tensile modulus 3 GPa pa66` — unit conversion

**Route: LLM** ✅ RUN routing · **conversion** ⟶ TRACED (needs `thefuzz`, not installed locally)

| Step | Line | Detail |
|---|---|---|
| is the unit exempt? | `post_processing.py:181` | `gpa` is not in the exclusion list → convert |
| general or exception table? | `:182-193` | `tensile modulus` is not one of the six exceptions → **general** |
| fuzzy-match the unit | `:107-109` | `token_sort_ratio > 85` against 1,442 `Incoming Unit` spellings |
| apply | `:204-223` | `ceed_unit = MPa`, `formula = (x)*1000` |

```
unit:  'gpa'  →  'gpa<->mpa'      # :206 records the conversion
value: '3'    →  '3000.0'         # min and max converted independently
```

**Data used:** `final_unit_conversion_table.csv` (1,496 rows, 1,442 distinct incoming spellings).

**Lesson.** The `<->` marker is deliberate — downstream can see that a conversion happened and
what it was. Each of the three conversions (`value`, `min`, `max`) is wrapped in its own bare
`try/except: pass`, so a bad formula fails silently.

## 15. `polyester housing` — when generic beats specific

**Route: LLM** ✅ RUN routing · **rule** ⟶ TRACED

The model answers `POLYMER: ["pbt"]`, because PBT **is** a polyester and that is what it saw in
training. But the user asked for the family, not the member:

```python
# ner_helper.py:1511-1514
if "pbt" in POLYMER and "polyester" in query and "pbt" not in query:
    POLYMER: pbt → polyester
```

The third condition is the careful part: if the user *did* write `pbt`, the rule stays out of the
way.

**Lesson.** A three-line rule encoding a taxonomy relationship the model over-applied. Cheaper
than retraining — which is the design philosophy of the entire rule layer.

## 18. `alternative to ultramid a3wg6 with better fuel resistance` — intent words change the rules

**Route: LLM** ✅ RUN routing

The word **`alternative`** does two jobs:

| Job | Line | Effect |
|---|---|---|
| blocks the AUTO_CERT fast path | `:1141` | this is a comparison, not a cert lookup |
| **protects** the model's COMPETITOR_GRADE label | `:1373-1374` | the reclassification rules leave it alone |

That second one is subtle. Normally a COMPETITOR_GRADE gets re-tested against the Celanese grade
list and may be moved. But when the query contains `tds`, `sds`, `alternative`, `offset`,
`replacement`, `similar`, `instead` or `competitor`, the code trusts the model — because those
words **signal competitor intent**.

Then `:1455-1469` strips the maker name from both ends:

```
'ultramid a3wg6'  →  'a3wg6'      # search indexes competitor grades without the maker
```

**Data used:** `normalized_competitor_names.json` (1,165 maker names and legal-form fragments).

📡 **LIVE** — the production model handled this shape well; the whole
`alternative to … / cross reference for … / we currently use …` family scored 100% precision on
COMPETITOR_GRADE across the 500-query run.

**Lesson.** The same string is treated differently depending on **surrounding intent words**.

## 19. `ps enclosure bondable` — two different out-of-scope mechanisms at once

**Route: LLM** ✅ RUN routing · **scope** ✅ RUN

```
internal   kept={}   active=True   flagged={'POLYMER': ['ps']}
```

Two independent things fire in `identify_out_of_scope_items`:

| Mechanism | Line | Direction | Detail |
|---|---|---|---|
| entity-value lookup | `:521-526` | value ∈ list | `ps` is in `OUT_OF_SCOPE_DATA['polymers']` (23 entries) |
| query pattern | `:528-531` | term ⊂ query | `bonding_pattern` + any polymer → `OTHERS: ["bondable"]` |

The first says *"we don't sell polystyrene"*. The second says *"we can't answer bonding questions"*
— a statement about **missing data**, not about the material.

> ⚠️ **If a valid BRAND were also present, the flag would silently switch off.**
> `post_processing.py:567` assigns rather than ORs. ✅ RUN:
>
> | Input | Flagged | `active` |
> |---|---|---|
> | `POLYMER:['ps']` | `{'POLYMER': ['ps']}` | `True` ✅ |
> | `POLYMER:['ps']` + `BRAND:['celanex']` | `{'POLYMER': ['ps']}` | **`False`** ❌ |
>
> So *"ps celanex enclosure"* strips the polymer and never tells the user. One-character fix.

**Lesson.** "Out of scope" covers two unrelated ideas — *we don't sell it* and *we don't hold that
data* — and they surface through the same field.

## 20. `nylon grade for Chlorine gas` — what happens with no guardrail

**Route: LLM** ✅ RUN routing · **output** 📡 LIVE

Real production output:

```jsonc
"POLYMER":     ["pa*"],
"APPLICATION": ["chlorine gas"],     // ⚠️ a chemical read as an application
"INDUSTRY":    ["chemical"]          // ⚠️ not one of the five documented industries
```

Two failures, and neither can be caught:

**`APPLICATION: chlorine gas`** — APPLICATION has **no validation against any reference data**.
The only processing is generic-word stripping (`:1613-1623`). Whatever the model says survives.

**`INDUSTRY: chemical`** — the documented vocabulary has exactly five values. ✅ RUN, the real
function:

```
get_industry('chlorine gas')      -> None
get_industry('fuel tank automotive') -> Automotive & Transportation
get_industry('electrical switch') -> Electrical & Electronics
get_industry('retail packaging')  -> Consumer Goods
get_industry('pharma tubing')     -> Medical & Pharma
```

`chlorine gas` maps to `None`, so **`"chemical"` came from the model, not the rule** — and nothing
downstream checks INDUSTRY against the five legal values.

**Lesson.** Six of the seventeen entities — REGION, DELIVERY_FORM, RAILWAY_CERT, WATER_CERT,
NSF_CERT and effectively APPLICATION — are matched against **no reference data at all**. They are
whatever the model says. That is also where the spurious `WATER_CERT: {standard: all, temp: [all]}`
values came from in the 500-query run: a query merely mentioning *water* produced a
drinking-water-approval entity, and nothing existed to reject it.

# What the twenty examples add up to

## The three questions that determine everything

```
1. Does the WHOLE query match one catalog entry?      → fast path, no LLM      (ex. 1-7, 10)
2. Is there a guard that says "this looks like X but isn't"?  → forced to LLM  (ex. 8, 9, 17)
3. Otherwise → LLM proposes, ~600 lines of rules dispose        (ex. 11-16, 18-20)
```

## Trace your own query

Everything marked ✅ RUN was produced without an endpoint, an API key or a container. The routing
harness lives at `KT learning/trace_query.py`:

```
python trace_query.py "your query here"
```

It runs the real `data_preprocessing()` and the fast-path predicates copied from
`ner_helper.py:938-1193`, and tells you which route a query takes and why. For scope questions,
see the snippet in [`17-…`](17-dependencies-files-explained.md) §16.6.
